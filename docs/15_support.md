# Задание 15. Обратная связь и план сопровождения

## Часть А. Работа с обращениями

### Issue tracker
GitHub Issues репозитория, шаблоны в `.github/ISSUE_TEMPLATE/` (баг, пожелание, вопрос).
Метки: `bug`, `enhancement`, `question`, `P0`, `P1`, `P2`, `P3`. Ссылку на репозиторий укажите и в карточке магазина
(«Контакты разработчика»).

### Приоритеты и SLA
| Приоритет | Критерий | Первый ответ | Исправление / план |
|---|---|---|---|
| **P0** | крэш при запуске/потеря данных/уязвимость | 4 ч | hotfix ≤ 24 ч |
| **P1** | сломан основной сценарий, есть обход | 1 рабочий день | ближайший патч ≤ 7 дней |
| **P2** | дефект второстепенной функции, UI | 3 рабочих дня | в ближайшем минорном релизе |
| **P3** | пожелание, вопрос, косметика | 5 рабочих дней | по backlog |

### Журнал обработки (минимум 3 обращения + 2 отзыва) — пример, замените реальными
| № | Тип | Обращение | Приоритет | Ответ / решение |
|---|---|---|---|---|
| #1 | Баг | «Приложение закрывается при нажатии “Поделиться” на пустом списке» | **P0/P1** | Воспроизведено, исправлено в 1.2.1, ответ пользователю: «Спасибо! Исправлено в версии 1.2.1, обновите приложение» |
| #2 | Пожелание | «Добавьте тёмную тему/синхронизацию» | P3 | Добавлено в backlog, метка `enhancement`, ответ с благодарностью и ориентиром по срокам |
| #3 | Вопрос | «Как перенести задачи на новый телефон?» | P3 | Ответ: сейчас хранятся локально, используйте «Поделиться», экспорт в планах; метка `question` |

### Ответы на отзывы в магазине (Play Console → Ratings and reviews → Reply)
1. ★★ «После обновления вылетает» → «Здравствуйте! Спасибо, что сообщили. Мы уже нашли причину и выпустили исправление в версии 1.2.1 — обновите приложение, пожалуйста. Если проблема останется, напишите на <e-mail> с моделью телефона.»
2. ★★★★★ «Простое и удобное» → «Спасибо за отзыв! Рады, что приложение пригодилось. Планируем добавить новые функции — делитесь идеями на GitHub.»
Скриншоты: список отзывов с ответами (в закрытом тестировании отзывы могут быть недоступны — тогда приложите текст тестовых ответов).

## Часть Б. Политика поддержки

### 1. Минимально поддерживаемая версия ОС
- Сейчас **minSdk 26 (Android 8.0)**. Поддерживается: текущая и 4 предыдущие основные версии Android, плюс версии, на которых
  у приложения более 3% активных пользователей (по Play Console → Statistics).
- Порядок повышения: решение раз в год; при доле старой версии < 3% и необходимости (новая API, требования безопасности)
  → предупреждение в «Что нового» за один релиз; повышение minSdk = **MAJOR** версия (SemVer, см. docs/02_versioning.md);
  пользователи старых ОС продолжают получать последнюю совместимую версию.

### 2. График обновлений
| Что | Когда |
|---|---|
| Зависимости (AndroidX, Material, Firebase) | раз в месяц, через Dependabot/Renovate PR + CI |
| Security-патчи библиотек | ≤ 7 дней после публикации CVE |
| AGP / Gradle / Kotlin | раз в квартал |
| **targetSdk** | ежегодно, до дедлайна Google Play (по состоянию на 2026 год — **API 36 (Android 16)** для новых приложений и обновлений с 31.08.2026; следующий — API 37 в 2027 — проверяйте [официальную страницу требований](https://developer.android.com/google/play/requirements/target-sdk)). Цель — начать миграцию на бета-SDK за 3–4 месяца до дедлайна |
| Требования магазинов (политика, Data Safety) | ревизия раз в квартал и при каждом новом SDK |

### 3. Жизненный цикл версий
| Статус | Определение |
|---|---|
| **Current** | последняя стабильная версия: все исправления и функции |
| **LTS / Maintained** | предыдущая MINOR-ветка: только исправления критических багов и уязвимостей в течение 6 месяцев |
| **EOL** | всё старше: исправления не выпускаются; через Remote Config `min_supported_version_code` приложение просит обновиться |
Мобильные приложения обновляются на стороне пользователя, поэтому EOL закрепляется принудительным обновлением (`UpdatePolicy`).

### 4. Резервное копирование
| Что | Как | Как часто |
|---|---|---|
| Репозиторий | зеркало на втором хостинге (GitLab/Gitea) + `git bundle` в зашифрованное хранилище | еженедельно, автоматически |
| keystore (upload key) | 2 зашифрованные копии в разных местах + пароли в менеджере паролей | при создании и после смены |
| Секреты CI | список названий в документации (значения — в менеджере паролей) | при изменении |
| `mapping.txt` каждой версии | `artifacts/mapping/<версия>/` + артефакты релиза в GitHub | при каждом релизе |
| `google-services.json`, учётка Play Console | доступ ≥ 2 владельцев, 2FA | постоянно |
Проверка восстановления — раз в квартал (открыть keystore, собрать приложение из чистого клона).

### 5. План реагирования на инциденты и уязвимости
1. **Обнаружение:** алерт Crashlytics, Android Vitals, отзыв, обращение, отчёт об уязвимости (контакт **security@<домен>** / GitHub Security Advisories).
2. **Оценка (≤ 4 ч):** назначить приоритет P0–P3, ответственного, завести issue.
3. **Остановка ущерба:** Halt rollout → выключить функцию через Remote Config → при необходимости поднять `min_supported_version_code`.
4. **Исправление:** hotfix-ветка от тега последней стабильной версии, PATCH+1, CI, быстрый rollout (10% → 100% по метрикам).
5. **Коммуникация:** ответы пользователям, запись в CHANGELOG, при утечке данных — уведомление пользователей и регуляторов в установленные законом сроки.
6. **Разбор (post-mortem, ≤ 5 дней):** причина, время T0–T4 и MTTR, что изменить в тестах/процессе; задача на предотвращение.
Уязвимости: приём по приватному каналу, подтверждение в течение 3 дней, исправление критических — ≤ 7 дней, публикация деталей после выхода исправления.
