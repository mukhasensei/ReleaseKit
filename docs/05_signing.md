# Задание 5. Подпись приложения

## Создание ключа
```bash
scripts/generate-keystore.sh release.jks   # keytool -genkeypair ... -alias upload -keyalg RSA -keysize 2048 -validity 10000
```
Файл `release.jks` лежит вне репозитория. Конфигурация подписи в `app/build.gradle` читает путь и пароли из
`KEYSTORE_FILE`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD` (env или `local.properties`).
Проверка подписи: `apksigner verify --print-certs app-release.apk` (из build-tools SDK).

## Upload key и app signing key (Play App Signing)
| | Upload key | App signing key |
|---|---|---|
| Кто хранит | вы | Google (в защищённом хранилище) |
| Чем подписан | AAB, который вы загружаете | APK, которые получают пользователи |
| Назначение | подтвердить Google, что загрузили именно вы | постоянная подпись приложения |
| При потере | можно запросить **сброс** ключа загрузки через поддержку Play Console и создать новый | Google хранит сам; потеря на вашей стороне невозможна |

Если приложение **не** использует Play App Signing (подпись только вашим ключом, APK в RuStore/GitHub) и ключ
потерян — вы **не сможете выпускать обновления** для существующих установок: Android не установит APK с другой подписью,
придётся публиковать новое приложение с новым applicationId, пользователи потеряют данные и отзывы.
Утечка ключа ещё опаснее: злоумышленник сможет выпустить «обновление» от вашего имени. При Play App Signing утечка
upload key лечится сбросом — приложение пользователей это не затрагивает.

## Как хранится keystore (заполните по факту)
1. Оригинал `release.jks` — на зашифрованном носителе (менеджер паролей/хранилище с шифрованием), не в репозитории.
2. Пароли — в менеджере паролей, отдельно от файла.
3. Копия во втором месте (офлайн-флешка / другой облачный аккаунт с шифрованием).
4. Для CI — файл закодирован `base64 -w0 release.jks` и лежит в GitHub Secrets (`KEYSTORE_BASE64`) вместе с паролями.
5. Раз в квартал проверяйте, что копия открывается: `keytool -list -keystore release.jks`.
